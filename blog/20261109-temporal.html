Beyond the Architect–Worker Model: Durable Orchestration for AI-Driven Development

Decoupling probabilistic agent reasoning from deterministic execution control with Temporal.

The Architect–Worker model provides an effective foundation for agent-assisted software development by separating high-level planning and technical judgment from delegated implementation. Yet as development workflows grow in complexity, the limitations of conversation-driven orchestration become increasingly apparent. Worker interruptions, overlapping assignments, failed CI runs, and incomplete handoffs repeatedly force the Architect to reconstruct execution histories, reconcile repository states, and determine where work can safely resume. Meanwhile, accumulating instructions, diagnostic logs, and intermediate reports consume valuable context, increasing the frequency of compaction and the risk of losing critical information. These recurring failures reveal a fundamental question: How can multi-agent development orchestration become more reliable, efficient, and responsive without sacrificing the autonomy of individual agents?

The diagnosis points to an architectural weakness rather than a deficiency in agent capability: execution coordination and state management remain coupled to the transient context of LLM conversations. Better prompts, larger context windows, or more sophisticated agent memory may alleviate individual symptoms, but they do not independently provide durable task ownership, recovery, or execution continuity. This motivated an exploration of Temporal as a durable orchestration layer for the existing Architect–Worker system. By separating probabilistic reasoning from deterministic workflow control, the proposed architecture allows agents to retain responsibility for planning and implementation while Temporal manages execution histories, dependencies, and retry coordination. The objective is not to replace intelligent agents with deterministic infrastructure, but to establish a more dependable foundation on which their collaboration can operate.

01ARCHITECTURAL PRINCIPLES

Separating Reasoning, Execution, and Evidence

The limitations of conversation-driven orchestration suggest that reliable multi-agent development requires more than effective delegation. It requires explicit ownership of three distinct concerns: technical reasoning, execution state, and verifiable development artifacts. When these responsibilities overlap, recovery becomes ambiguous, operational histories accumulate in conversational context, and agents are repeatedly required to reconstruct information that should persist independently of their sessions.

The proposed architecture establishes three complementary boundaries, assigning each responsibility to a dedicated system component:

  • AI Agents — The Probabilistic Reasoning Layer: Operating through dedicated Codex Desktop sessions, Architect and implementation agents interpret requirements, establish development plans, generate and review code, and resolve technical uncertainties. Their autonomy is preserved, while routine execution tracking is delegated to infrastructure rather than another supervisory agent.
  • Temporal — The Durable Execution Layer: Manages workflow lifecycles, task dependencies, scheduling, timers, retries, and execution histories. Its deterministic orchestration model provides continuity across process failures and agent-session interruptions without attempting to reproduce the probabilistic reasoning performed by the agents themselves.
  • Git — The Authoritative Code Ledger: Maintains the versioned history of source code, branches, commits, and changes. It provides durable evidence of development outcomes, enabling interrupted operations to be reconciled against existing artifacts rather than blindly repeated. CI and other verification systems complement this record by establishing whether changes satisfy their acceptance criteria.

These boundaries distinguish decision-making authority, execution coordination, and evidence of completed work. Temporal determines when and under what conditions activities should proceed; agents determine how technical problems should be addressed; and Git preserves the resulting code changes. None of these components independently guarantees end-to-end correctness. Their reliability emerges from explicit interfaces, verifiable artifacts, and recovery policies that reconcile external side effects with recorded workflow state.

By removing routine coordination from the Architect's conversational context, this separation is intended to reduce redundant reporting, preserve execution continuity across sessions, and reserve reasoning capacity for decisions that require technical judgment. It also avoids introducing an additional supervisory LLM, whose own state and availability would create further coordination requirements.

The governing principle is straightforward: Temporal remembers what happened; Git records what changed; the Architect determines what should happen next.

02MECHANICS

How Temporal Works: The Mechanics of Durable Execution

Conventional orchestration scripts often maintain execution state in process memory, local files, or application-managed checkpoints. While adequate for short-lived tasks, these approaches become increasingly fragile when development workflows span multiple agents, repository changes, CI runs, and human approvals. Temporal addresses this limitation through durable execution based on event histories and task queues, preserving workflow progression independently of any continuously running application process. Its purpose is not to make LLM behavior deterministic, but to establish a recoverable coordination layer around inherently nondeterministic development activities.

Workflows and Activities: Separating Control from Execution

Temporal's programming model distinguishes between two complementary abstractions:

  • Workflows — Deterministic Coordination: Workflows define dependencies, conditional branches, timers, and execution sequences. Their code must remain compatible with Temporal's replay mechanism, excluding arbitrary external API calls, filesystem modifications, and other nondeterministic operations except through SDK-supported deterministic mechanisms.
  • Activities — External Execution: Activities perform operations involving external systems, including LLM invocations, coding-agent execution, Git modifications, CI runs, and database writes. They may fail, time out, or be retried according to explicit execution policies.

This separation establishes a fundamental boundary: Workflows determine which operations should occur and under what conditions; Activities perform those operations. It allows deterministic coordination to govern development processes even when individual agents produce probabilistic results.

Code Replay, Activity Retry, and Their Limits

Temporal's recovery mechanism relies on event-history replay rather than conventional process snapshots. Snapshot-based approaches restore previously captured application state, often requiring additional mechanisms to recover subsequent progress. Temporal instead maintains an ordered history of significant workflow events, including Activity completions, timers, and external signals. When a workflow worker loses its in-memory state, another compatible worker deterministically re-executes the workflow code against this history. The Temporal SDK supplies previously recorded outcomes, restoring the workflow's logical control state without repeating completed Activities.

This reconstruction involves no inference or reproduction of an agent's reasoning. An LLM-driven coding task may depend on probabilistic model outputs, evolving conversational context, repository state, and external tool responses that cannot be reproduced from command histories alone. Temporal preserves the recorded outcomes of completed Activities, not the reasoning trajectories that produced them. Temporal provides deterministic control over the execution of probabilistic agents, not deterministic control over the agents' reasoning.

Two distinct mechanisms govern recovery. Workflow Replay reconstructs orchestration state after a workflow worker restart or cache loss, without inherently repeating completed external operations. Activity Retry, by contrast, reattempts an Activity following a failure or timeout under its configured retry policy. Because a retried Activity may repeat external side effects, operations involving Git, databases, or LLM agents require idempotency and explicit state reconciliation. These mechanisms are independent: workflow replay does not necessarily trigger Activity retries, and Activity retries do not inherently require workflow replay.

A Concrete Recovery Sequence

Consider an Architect delegating a feature implementation to a coding agent, followed by automated testing and review.

  1. Planning and implementation. The Architect completes a planning Activity, whose result is recorded by Temporal. An implementation Activity then invokes a coding agent, which modifies source files and creates Git commit abc123.
  2. Failure before acknowledgment. The Activity worker crashes after creating the commit but before Temporal records successful completion. The code change exists, yet the Activity's outcome remains unconfirmed.
  3. Activity Retry. Following the applicable timeout and retry policy, Temporal schedules another attempt. This is a retry of the external operation, not a replay of the workflow's control state.
  4. External reconciliation. Before invoking the coding agent again, the Activity inspects the stable task identifier, repository branch, existing commits, and persisted job records. It verifies that commit abc123 satisfies the assignment and returns that reference instead of repeating the LLM-driven work.
  5. Durable continuation. Temporal records the successful Activity result, and the workflow advances to testing and review without requiring the Architect to reconstruct the agent's previous actions.
  6. Workflow Replay. If the workflow worker subsequently restarts, a compatible worker reconstructs its control state from event history. Previously completed planning and implementation Activities are not executed again, and an already-running testing Activity need not restart merely because the workflow worker was interrupted.

The example illustrates the complementary roles of the recovery mechanisms: Activity Retry reattempts unconfirmed work, Workflow Replay restores coordination state, and external reconciliation verifies what actually happened outside Temporal. The reconciliation logic belongs to the application; Temporal does not independently inspect Git or determine whether an interrupted agent completed its assignment.

Recovery Matrix

Failure scenario Recovery mechanism Expected behavior
Workflow worker crashes Workflow Replay Reconstruct control state without repeating completed Activities.
Activity fails before external side effects Activity Retry Re-execute according to the retry policy.

Why Replay Still Matters

The limitations of Activity execution clarify rather than diminish the significance of Workflow Replay. Unlike a standalone snapshot, Temporal's event history provides an ordered record from which compatible workflow code can reconstruct established decisions, completed Activities, and outstanding dependencies. Snapshot-based architectures can achieve similar guarantees when supplemented with event logs and transactional recovery mechanisms; Temporal's advantage lies in integrating these capabilities into its programming and execution model.

For agent-assisted development, the broader significance is continuity of coordination without continuity of reasoning sessions. A workflow spanning multiple coding agents, CI runs, human approvals, and interrupted sessions can retain its operational state without requiring any individual conversation to remain active. Completed work can be recognized, unresolved operations can be retried or reconciled, and the Architect can concentrate on decisions rather than reconstructing execution history.

Temporal does not reproduce how an agent reached a conclusion. It preserves the execution context necessary to act on that conclusion and move the development process forward.

03TEMPORAL ARCHITECTURE

Inside Temporal: Execution State, Task Queues, and Workers

Temporal separates durable workflow coordination from application-level execution. The Temporal Server maintains execution histories, manages workflow state, and coordinates task delivery, while independently deployed workers execute workflow definitions and Activities through the server's APIs. This separation allows workflows to survive individual worker failures without requiring the server itself to execute application logic.

The Temporal Server

A self-hosted Temporal deployment comprises several cooperating services with distinct responsibilities:

  • Frontend Service — API Access: Provides the primary gRPC interface for clients and workers, handling workflow requests, Queries, Signals, Updates, and worker communication.
  • History Service — Workflow State Management: Coordinates workflow state transitions and maintains execution histories through the persistence layer, enabling durable recovery.
  • Matching Service — Task Distribution: Matches pending workflow and Activity tasks with workers polling the corresponding task queues, decoupling scheduling from worker availability.
  • Persistence Layer — Durable Storage: Stores execution histories, workflow state, and service metadata. Production deployments typically use supported databases such as PostgreSQL or MySQL, while local development may use lighter storage configurations.

Together, these components maintain execution continuity independently of application processes. The Temporal Server coordinates and persists workflow state but does not execute application-defined Workflows or Activities; those responsibilities belong to Temporal Workers.

Temporal Workers: Where Application Logic Executes

Temporal Workers are long-running processes that poll task queues and execute registered workflow and Activity implementations. Workflow Workers execute deterministic orchestration logic and may cache workflow state in memory to reduce replay overhead. When this state is lost, compatible workers can reconstruct it from the recorded event history. Activity Workers, by contrast, perform external operations such as invoking LLMs, modifying Git repositories, running tests, or interacting with APIs. Their side effects, resource consumption, and retry behavior require explicit safeguards.

A single Python worker process can host both Workflows and Activities, although separate task queues and worker pools may be introduced when workloads require independent scaling or isolation. This division establishes a clear operational boundary: the server preserves execution state, workers execute application logic, and external systems retain authority over their artifacts and side effects.

Implications for Agent-Assisted Development

In the proposed Automation project integration, Python Temporal Workers would coordinate existing Codex Desktop agents through narrowly scoped execution adapters rather than replacing their established development environments. Activities would dispatch or monitor bounded assignments, collect structured results, and retain references to Git commits, CI reports, and other durable artifacts. The agents would remain responsible for reasoning and implementation, while adapters enforce execution permissions, resource limits, and recovery policies.

The architecture also permits incremental scaling. Coding, testing, CI monitoring, and review could eventually operate through separate worker pools, but such distribution is not an initial requirement. A host-managed Temporal Server and a small number of Python workers should provide a sufficient starting point for evaluating reliability and context efficiency. The objective is not to distribute agent execution indiscriminately, but to establish a durable coordination layer that remains independent of individual agents and their conversational sessions.

04DECLARATIVE ORCHESTRATION

Temporal as an Execution Backend for a Recipe DSL

Although Temporal provides durable workflow orchestration, encoding every development procedure as a dedicated Python workflow would introduce unnecessary coupling between task definitions and execution infrastructure. A more flexible approach is to retain a declarative Recipe DSL that describes development milestones, dependencies, execution policies, and approval requirements, while Temporal serves as the durable execution backend. This separation allows development procedures to evolve independently of their underlying orchestration implementation.

Declarative Workflow Definition

A simplified development recipe might take the following form:

name: automation-development
version: "1.0"

milestones:
  - id: plan
    agent: automation-architect
    action: define-bounded-tasks

  - id: implement
    agent: dev-worker
    action: implement-and-commit
    depends_on: [plan]

  - id: verify
    agent: review-worker
    action: run-targeted-tests-and-review
    depends_on: [implement]

  - id: security-gate
    action: run-security-scans
    tools: [ruff, bandit, trivy, gitleaks]
    depends_on: [verify]
    on_failure: block-merge

  - id: merge
    action: merge-verified-pr
    depends_on: [security-gate]
    requires_approval: true

The recipe specifies the intended development process without prescribing how each agent or tool must execute its assignment. Here, implementation follows planning, validation follows implementation, and human approval is required before the workflow concludes. Other recipes may introduce earlier approval gates when security-sensitive operations, repository permissions, or infrastructure changes require authorization before execution.

Execution and Agent Integration

The proposed architecture uses a reusable recipe interpreter implemented as a Temporal Workflow, avoiding the need to write a separate workflow implementation for every development procedure. When an Architect submits a recipe, the system validates its schema, dependencies, task references, and permissions, then associates the validated definition with a stable workflow identifier and an immutable recipe version or snapshot. The workflow schedules Activities according to the dependency graph, records their outcomes, and advances milestones as their prerequisites are satisfied. For human approval gates, it can wait durably for an authorized Signal or Update without keeping an agent process active.

The Codex Desktop integration provides the interface to this execution layer. Authorized Architect sessions can inspect workflow progress through Temporal's MCP interface and initiate controlled operations through Python tools backed by the Temporal SDK. This separation avoids introducing another persistent supervisory agent: Temporal maintains execution state, while the existing Architect remains responsible for planning and decisions. At the time of this design, the official Temporal MCP implementation is read-only and pre-release, so workflow submission, approval, and cancellation are assigned to a separate authorized interface.

The declarative approach does not eliminate the need for application-level safeguards. The recipe interpreter must validate acyclic dependencies, enforce concurrency limits, maintain stable task identities, and handle retry policies and recipe-version compatibility. Temporal supplies the durable execution primitives but does not automatically enforce the semantics of a custom DSL. With these responsibilities explicitly defined, the result is a reusable coordination model in which development procedures remain declarative, execution remains durable, and agent reasoning remains independent of the workflow infrastructure.

05DEVELOPER CI

Where Durable Execution Improves Agent-Assisted Development

Traditional CI systems are designed to execute predefined build, test, and deployment procedures. Agent-assisted development introduces a broader coordination challenge involving probabilistic reasoning, evolving implementation plans, asynchronous worker execution, and human intervention. A coding agent may produce an incomplete change, a reviewer may request architectural revisions, or a worker may terminate after committing code but before reporting completion. The challenge is therefore not merely to restart failed commands, but to recover the development process without losing verified progress or unnecessarily repeating completed work.

Temporal provides a durable foundation for addressing these challenges by separating workflow coordination from agent execution. However, its guarantees concern orchestration rather than the correctness of external operations. The following distinctions clarify both its contributions and the responsibilities that remain with the surrounding development system.

Recurring difficulty Temporal's contribution Remaining responsibility
Architect context loss Durable milestone execution state Agent memory and handoffs
Interrupted workers Activity retries and recovery coordination Worktree and job reconciliation
Duplicate assignments Stable workflow and task identifiers Ownership and idempotency
Repeated CI failures Explicit failure branches and retry policies Diagnosis and corrective changes
Expensive LLM operations Scheduling and concurrency controls Token budgets and caching
Pending human approvals Durable waiting for approval events Authentication and authorization
Evolving workflows Workflow versioning mechanisms Compatible recipe and code migrations

The distinction between coordination and execution becomes particularly important during recovery. Suppose an implementation worker successfully creates a Git commit but terminates before reporting completion. A naïve retry could launch another coding session and produce redundant changes. A recovery-aware Activity instead inspects the existing branch, worktree, commit history, and task identifier before deciding whether another execution attempt is necessary. Temporal coordinates the retry; Git provides the evidence needed to reconcile it safely.

The same principle applies to CI failures. Repeatedly running an unchanged test suite may consume resources without advancing development when the underlying failure is deterministic. A reliable workflow should distinguish transient infrastructure errors from implementation defects, applying bounded retries to the former while escalating the latter for agent-driven diagnosis and correction. Likewise, expensive LLM operations require explicit concurrency limits, caching, and usage budgets rather than indiscriminate retries.

The objective is not to automate every technical decision or eliminate the possibility of failure. It is to make the execution surrounding agent decisions durable, observable, and recoverable, while preserving clear responsibility for code correctness, security verification, and human authorization.

06SYSTEM ARCHITECTURE

Durable Orchestration Without Conversational Overhead

The existing Codex Desktop environment follows an Architect–Worker model, in which a project-level Architect oversees planning, task decomposition, and technical decisions while specialized workers undertake implementation, testing, and review. This separation has proven effective for organizing agent-assisted development. Its principal limitation, however, lies in the coordination between these roles: execution progress, intermediate reports, and recovery decisions remain closely coupled to individual conversational sessions.

The architectural reform described in this section is a proposed extension of that existing system, rather than a description of a completed Temporal deployment. The current environment already includes sandboxed Codex Desktop agent sessions on an Arch Linux host, Python virtual environments, non-root Git execution, bwrap isolation, and systemd-managed services. The Temporal CLI and Python SDK have also been installed. What remains to be implemented and verified is the host-managed Temporal Server with durable persistence, Python Temporal Workers, and the interfaces connecting Temporal to the existing agents.

The proposed architecture preserves the established agent hierarchy while introducing Temporal as an independent orchestration layer. The Architect would retain authority over planning, delegation, and technical decisions, while implementation workers would continue performing bounded development tasks. Temporal would assume responsibility for durable workflow progression, task scheduling, and recovery coordination.

The central objective extends beyond execution reliability. By externalizing operational state and communication, the reform seeks to decouple the continuity of development workflows from the continuity of agent conversations. Routine worker reports, retry events, and diagnostic logs would no longer need to accumulate in the Architect's conversational context. Instead, the Architect could retrieve concise, decision-relevant information when necessary.

Component Responsibilities and Boundaries

The target architecture assigns explicit responsibilities to the following components. The Architect–Worker hierarchy and existing development tools are already in use; the Temporal infrastructure and integration interfaces represent the planned additions.

  • Temporal Server — Durable Coordination (Proposed): The server would maintain workflow execution histories, task queues, timers, and persistent orchestration state. Operating independently of agent sessions, it would coordinate workflow scheduling and recovery without executing application-specific Activities or interpreting agent decisions.
  • Python Temporal Workers — Workflow Execution (Proposed): Workers would poll designated task queues, execute deterministic workflow code, and perform Activities that interact with development tools through narrowly scoped adapters. Nondeterministic operations—including LLM invocations, Git modifications, and external API calls—would remain outside deterministic workflow logic.
  • Temporal MCP and Python Tools — Agent Interfaces (Proposed): MCP would provide authorized Codex sessions with selective read access to workflow histories, execution status, and diagnostics. Separate permission-checked Python tools would expose state-changing operations through the Temporal SDK. These interfaces would not constitute autonomous agents or implicitly establish bidirectional messaging between Codex sessions.
  • Automation Architect — Planning and Technical Judgment (Existing Role, Extended Interface): The Architect currently defines milestones, decomposes tasks, establishes dependencies, and evaluates results requiring technical decisions. Under the proposed integration, it would additionally initiate and inspect Temporal workflows through authorized tools, while relying on persistent execution records instead of conversational history for routine progress tracking.
  • Implementation Workers — Bounded Development Execution (Existing Role, Extended Interface): Specialized agents already perform coding, testing, and review within sandboxed Codex Desktop environments. The proposed integration would introduce structured assignments with stable task identifiers, explicit acceptance criteria, and durable artifact references. Recovery would rely on reconciling existing work rather than reproducing interrupted agent reasoning.
  • Git and CI — Authoritative Development Evidence (Existing Infrastructure): Git maintains the versioned record of source changes, while CI provides evidence of build and test outcomes. Temporal would store references to these artifacts rather than replace their authority. Before retrying interrupted operations, Activities would reconcile recorded task state against existing commits, branches, external job identifiers, and test results.

The target topology deliberately excludes a dedicated Temporal Agent. Introducing another LLM-based supervisory component would add coordination overhead without necessarily improving reliability. Instead, the existing Architect would retain decision-making authority, while Temporal and its Python workers would maintain execution independently of any particular chat session.

Communication Flow

The architecture separates read-only workflow inspection from state-changing operations through two communication paths: 

Read:  Codex Agent → Temporal MCP Server → Temporal Server

Write: Codex Agent → Python Tool → Temporal Python SDK
                                → gRPC → Temporal Server

The MCP interface provides authorized agents with access to workflow histories, execution status, and diagnostics. State-changing operations—including workflow submission, approval, and cancellation—are handled through controlled Python tools using the Temporal SDK, which communicates with the server over gRPC.

This separation preserves explicit authorization boundaries without requiring agents to implement low-level communication protocols or maintain workflow execution state themselves.

Deployment and Security Boundaries

The planned integration would preserve the existing Python virtual environments, non-root Git execution, bwrap sandboxing, and systemd-managed services. The Temporal Server is intended to run as persistent infrastructure on the Arch Linux host, while Codex agents remain isolated within their established sandboxed execution environments.

Communication across this boundary would require explicitly authorized interfaces, without granting agents unrestricted access to host filesystems, credentials, or privileged services. Temporal API access would likewise need to be controlled, since workflow submission, signaling, and cancellation can affect other running tasks.

The intended separation is therefore between durable orchestration infrastructure, probabilistic agent execution, and the security boundaries governing their interaction.

Selective Context Injection

The separation of execution state from conversational context is ultimately realized through the system's reporting policy.

In the existing conversation-driven orchestration model, the Architect may receive worker instructions, intermediate results, retry notifications, and diagnostic outputs. As development complexity increases, this accumulation consumes context disproportionately to the decisions being made, requiring frequent compaction and introducing opportunities for information loss.

Under the proposed architecture, operational records would remain in their respective systems: Temporal would retain workflow execution histories, Git would preserve code changes, and CI or artifact storage would retain test results and diagnostic logs. The Architect would receive compact summaries containing task identifiers, completion status, relevant artifact references, and unresolved issues.

Detailed information would be retrieved selectively when an exception, architectural decision, or verification requirement warranted further inspection. Routine progress monitoring could rely on structured state queries rather than repeated LLM-driven polling or conversational reports.

This approach would not eliminate the need for agent memory or session handoffs. Temporal preserves what happened during workflow execution, while project memory retains why particular architectural decisions were made, together with enduring constraints and accumulated technical knowledge. These functions would remain complementary.

The expected outcome is a development system in which the Architect's context becomes a deliberately managed resource rather than a repository for operational history. Temporal would maintain continuity of execution; the Architect would maintain continuity of judgment.

07CONCLUSION

Toward Durable Agent-Assisted Software Engineering

The evolution from standalone AI agents to coordinated development systems reveals an architectural challenge that advances in model capability alone cannot resolve. The Architect–Worker model provides an effective division of cognitive labor, but reliable collaboration requires more than capable reasoning and delegated execution. It demands persistent task ownership, recoverable execution state, verifiable outcomes, and clearly defined boundaries between decision-making and operational control. Without these foundations, increasingly capable agents risk becoming components of an increasingly fragile system.

Temporal offers a promising approach by decoupling workflow continuity from the continuity of individual agent sessions. Its durable execution model allows deterministic orchestration to coordinate inherently probabilistic development activities, while Git and external artifacts provide evidence of work performed. The objective is not to constrain agent autonomy or reproduce their reasoning trajectories, but to establish an execution framework in which interruptions can be recovered, completed work can be reconciled, and coordination no longer depends on the Architect's conversational memory.

Nevertheless, durable orchestration should not be mistaken for end-to-end execution correctness. Temporal cannot reproduce nondeterministic LLM decisions, guarantee exactly-once execution of external side effects, or independently determine whether an interrupted coding agent has completed its assignment. These responsibilities remain with application-level mechanisms, including idempotent operations, persistent artifact references, Git state reconciliation, and explicit acceptance criteria. Nor does Temporal inherently provide agent communication, semantic task decomposition, or intelligent exception handling; these capabilities must be supplied by the existing agents and their integration adapters. Workflow durability therefore establishes a foundation for reliability rather than eliminating the need for careful system design.

The Automation project serves as the initial testbed for this architectural reform. Rather than pursuing comprehensive autonomy from the outset, the implementation will focus on measurable objectives: recovery from worker interruptions, prevention of duplicate development work, reduced orchestration overhead, and more selective use of the Architect's context. These benefits remain hypotheses to be validated through implementation, controlled failure testing, and operational observation—not guarantees conferred by adopting Temporal alone.

Ultimately, the next step toward reliable agent-assisted software engineering may lie less in making agents more intelligent than in making the systems coordinating them more dependable. By separating probabilistic reasoning from durable execution control, the proposed architecture aims to preserve the flexibility of autonomous agents while introducing the continuity, accountability, and operational discipline required for sustained software development. The result is a shift from conversations that coordinate work toward infrastructure that preserves its progress—allowing agents to concentrate on the decisions that warrant their intelligence.
